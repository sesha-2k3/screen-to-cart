# Requirements Document

## Introduction

Phase 0 of the Screen to Cart build plan (`docs/screen-to-cart-build-plan.md`, sections 4, 5 and 6) sets up the repository skeleton: a uv-managed Python 3.12 FastAPI backend, a WXT + React + TypeScript (Manifest V3) extension with a side panel, Docker Compose with Postgres 16 + pgvector, env-driven configuration, an LLM provider factory, Alembic migrations, and Langfuse tracing.

Phase 0 is done when `docker compose up` brings up the database and the API, the side panel shows "backend OK", and a test request appears as a named trace in Langfuse.

Out of scope for Phase 0: the per-model rate limiter, record/replay behaviour, LangGraph nodes, retailer adapters, frame capture, `/lookup` and `/identify`.

## Glossary

- **Backend**: The uv project `screen-to-cart-backend` in `backend/`, a Python 3.12 FastAPI application.
- **Backend_Project**: The `backend/pyproject.toml`, `backend/uv.lock` and `backend/.python-version` files that define the Backend's dependencies and Python version.
- **Backend_Image**: The Docker image built from `backend/Dockerfile`.
- **Extension**: The WXT + React + TypeScript Manifest V3 browser extension in `extension/`, package name `screen-to-cart-extension`.
- **Side_Panel**: The Extension's React UI rendered through `chrome.sidePanel`, in `extension/entrypoints/sidepanel/`.
- **API_Types**: The file `extension/lib/api-types.ts`, generated by `openapi-typescript` from the Backend's `/openapi.json`.
- **API_Client**: The typed client in `extension/lib/api.ts`, built on `openapi-fetch` and the API_Types.
- **Compose_Stack**: The services defined in `docker-compose.yml` with project `name: screen-to-cart`.
- **Database**: The Postgres 16 + pgvector service in the Compose_Stack, running the `pgvector/pgvector:pg16` image with database name `screen_to_cart`.
- **Env_Example**: The committed file `.env.example` listing environment variable names without secret values.
- **Env_File**: The user's local `.env` file, edited only by the user.
- **Settings**: The pydantic-settings class in `backend/app/config.py` that reads configuration from the environment and the Env_File.
- **Model_Spec**: A string of the form `provider:model` (for example `groq:openai/gpt-oss-20b`) that names an LLM provider and model.
- **Role**: One of the LLM roles `identify_vision`, `disambiguate`, `refine` or `sponsorship`.
- **LLM_Factory**: The function `get_llm(role)` in `backend/app/llm/` that returns a LangChain chat model for a Role.
- **Migrations**: The Alembic setup (async engine) in `backend/app/db/`, including its migration scripts.
- **Observability_Module**: The module `backend/app/observability.py` that sets up the Langfuse client and tracing helpers.
- **Health_Endpoint**: The `GET /health` route in `backend/app/main.py`.
- **Provider_Tag**: A Langfuse trace tag naming the active LLM provider tier, `groq-free` in Phase 0.
- **Test_Suite**: The pytest tests in `backend/tests/`.
- **Setup_Guide**: The section of the committed root `README.md` that documents the variables the user must set in the Env_File.
- **LlmConfigError**: The base exception class defined by the LLM_Factory for LLM configuration errors.
- **ProviderNotInstalledError**: The exception class defined by the LLM_Factory, a subclass of LlmConfigError, raised when the package for a configured LLM provider is not installed.
- **Tracing_Wrapper**: The `@observe()` span and the `propagate_attributes` context that the Health_Endpoint runs inside.

## Requirements

### Requirement 1: Backend project and dependencies

**User Story:** As the developer, I want the Backend set up as a uv project with every Phase 0 dependency locked, so that every machine and the Docker image install the same versions.

#### Acceptance Criteria

1. THE Backend_Project SHALL be created with `uv init backend --app --python 3.12 --name screen-to-cart-backend`.
2. THE Backend_Project SHALL contain a `.python-version` file with the value `3.12`.
3. THE Backend_Project SHALL declare in `pyproject.toml` a `[[tool.uv.index]]` entry named `pytorch-cpu` with URL `https://download.pytorch.org/whl/cpu` and `explicit = true`.
4. THE Backend_Project SHALL declare in `pyproject.toml` a `[tool.uv.sources]` entry mapping `torch` to the `pytorch-cpu` index with the marker `sys_platform != 'darwin'`.
5. WHEN `torch` is added to the Backend_Project, THE Backend_Project SHALL already contain the `pytorch-cpu` index and the `torch` source entry.
6. THE Backend_Project SHALL list as runtime dependencies, added with `uv add`: fastapi, uvicorn[standard], sse-starlette, pydantic, pydantic-settings, langgraph, langchain-core, langchain-groq, langfuse, httpx, sqlalchemy[asyncio], asyncpg, alembic, pgvector, opencv-python-headless, pillow, numpy, torch, transformers, sentencepiece and rapidfuzz.
7. THE Backend_Project SHALL list in the dev group, added with `uv add --dev`: pytest, pytest-asyncio, respx, ruff and mypy.
8. THE Backend_Project SHALL list in the `eval` group, added with `uv add --group eval`: pandas and matplotlib.
9. THE Backend_Project SHALL declare dependencies without explicit version pins, leaving version resolution to `uv lock`.
10. THE Backend_Project SHALL include a committed `backend/uv.lock` file that is consistent with `pyproject.toml`.

### Requirement 2: Backend Docker image

**User Story:** As the developer, I want a Dockerfile for the Backend that installs exactly what is locked, so that the production image is reproducible and excludes dev and eval tools.

#### Acceptance Criteria

1. THE Backend_Image SHALL install Python dependencies with `uv sync --frozen --no-dev`.
2. THE Backend_Image SHALL exclude the packages from the dev group and the `eval` group.
3. WHEN the Backend_Image container starts, THE Backend SHALL serve the FastAPI application over HTTP on a port published by the Compose_Stack.

### Requirement 3: Docker Compose stack

**User Story:** As the developer, I want one command to start the database and the API, so that local setup is repeatable.

#### Acceptance Criteria

1. THE Compose_Stack SHALL declare `name: screen-to-cart` at the top of `docker-compose.yml`.
2. THE Compose_Stack SHALL define a Database service using the `pgvector/pgvector:pg16` image with database name `screen_to_cart`.
3. THE Compose_Stack SHALL define a backend service built from `backend/Dockerfile`.
4. THE Compose_Stack SHALL supply the backend service with configuration from the Env_File by reference, without copying Env_File values into `docker-compose.yml`.
5. WHEN `docker compose up` is run with a valid Env_File, THE Compose_Stack SHALL start the Database and the Backend, and the Health_Endpoint SHALL return a success response from the host.
6. WHEN the backend service starts, THE Compose_Stack SHALL start the backend service after the Database service is accepting connections.

### Requirement 4: Environment variable template

**User Story:** As the developer, I want a committed list of every environment variable, so that I know what to set in my own Env_File without secrets entering the repository.

#### Acceptance Criteria

1. THE Env_Example SHALL contain the variable names from section 5 of the build plan: DATABASE_URL, GROQ_API_KEY, IDENTIFY_VISION_MODEL, DISAMBIGUATE_MODEL, REFINE_MODEL, LLM_MODE, LANGFUSE_PUBLIC_KEY, LANGFUSE_SECRET_KEY, LANGFUSE_BASE_URL, EBAY_CLIENT_ID, EBAY_CLIENT_SECRET, BESTBUY_API_KEY and SIGLIP_MODEL.
2. THE Env_Example SHALL keep the non-secret example values from section 5 of the build plan for DATABASE_URL, IDENTIFY_VISION_MODEL, DISAMBIGUATE_MODEL, REFINE_MODEL, LLM_MODE, LANGFUSE_BASE_URL and SIGLIP_MODEL.
3. THE Env_Example SHALL leave GROQ_API_KEY, LANGFUSE_PUBLIC_KEY, LANGFUSE_SECRET_KEY, EBAY_CLIENT_ID, EBAY_CLIENT_SECRET and BESTBUY_API_KEY without values.
4. THE Env_Example SHALL contain the variable SPONSORSHIP_MODEL with no value.
5. THE Env_Example SHALL contain the commented line `# Later: ANTHROPIC_API_KEY=` from section 5 of the build plan.
6. THE Backend SHALL read secrets only from the environment or the Env_File through the Settings.
7. WHEN Phase 0 setup is complete, THE developer workflow SHALL report to the user the list of variables the user must set in the Env_File, and the Env_File SHALL be modified only by the user.
8. THE Setup_Guide SHALL list every variable the user must set in the Env_File.
9. THE Setup_Guide SHALL state, for each listed variable, the variable name, the file the variable is set in, where to obtain the value, and whether the variable is required in Phase 0.

### Requirement 5: Settings

**User Story:** As the developer, I want typed, env-driven configuration with model names per role, so that switching providers is a configuration change.

#### Acceptance Criteria

1. THE Settings SHALL load configuration from environment variables and the Env_File using pydantic-settings.
2. THE Settings SHALL expose a Model_Spec field for each Role: identify_vision from IDENTIFY_VISION_MODEL, disambiguate from DISAMBIGUATE_MODEL, refine from REFINE_MODEL and sponsorship from SPONSORSHIP_MODEL.
3. IF SPONSORSHIP_MODEL is unset or empty, THEN THE Settings SHALL use the value of REFINE_MODEL as the sponsorship Model_Spec.
4. THE Settings SHALL expose an LLM_MODE field accepting exactly the values `live`, `record` and `replay`.
5. IF LLM_MODE is set to a value other than `live`, `record` or `replay`, THEN THE Settings SHALL raise a validation error naming LLM_MODE.
6. THE Settings SHALL expose fields for DATABASE_URL, GROQ_API_KEY, LANGFUSE_PUBLIC_KEY, LANGFUSE_SECRET_KEY, LANGFUSE_BASE_URL, EBAY_CLIENT_ID, EBAY_CLIENT_SECRET, BESTBUY_API_KEY and SIGLIP_MODEL.
7. THE Settings SHALL contain no hard-coded secret values.
8. IF a variable is set both as an environment variable and in the Env_File, THEN THE Settings SHALL use the environment variable value.
9. WHEN one variable is set only as an environment variable and another variable is set only in the Env_File, THE Settings SHALL load both values into the same Settings instance.

### Requirement 6: LLM provider factory

**User Story:** As the developer, I want every node to get its model from one factory, so that model and provider choices live only in configuration.

#### Acceptance Criteria

1. WHEN `get_llm(role)` is called with a Role, THE LLM_Factory SHALL read the Role's Model_Spec from the Settings.
2. THE LLM_Factory SHALL parse a Model_Spec by splitting on the first `:` into a provider name and a model name.
3. WHEN the provider name is `groq`, THE LLM_Factory SHALL return a `ChatGroq` instance configured with the parsed model name and the GROQ_API_KEY from the Settings.
4. IF the provider name is `anthropic` and `langchain-anthropic` is not installed, THEN THE LLM_Factory SHALL raise a ProviderNotInstalledError, instead of propagating an ImportError, with a message stating that `langchain-anthropic` must be added with `uv add langchain-anthropic`.
5. IF `get_llm` is called with a value that is not a Role, THEN THE LLM_Factory SHALL raise an error naming the invalid value and listing the valid Roles.
6. IF the provider name of a Model_Spec is not a supported provider, THEN THE LLM_Factory SHALL raise an error naming the unsupported provider and the Role.
7. IF a Model_Spec has no `:` separator, an empty provider name or an empty model name, THEN THE LLM_Factory SHALL raise an error naming the Role and the malformed Model_Spec.
8. THE Backend SHALL contain model names only in configuration sources (Env_Example and Settings defaults derived from environment), with no model name literals in the LLM_Factory or other application code.
9. WHEN `get_llm(role)` returns a chat model, THE LLM_Factory SHALL construct the chat model without sending any request to the LLM provider.
10. WHEN the provider name is `groq`, THE LLM_Factory SHALL return the exact `ChatGroq` instance the LLM_Factory constructed, without wrapping, caching or proxying the instance.
11. THE LLM_Factory SHALL define ProviderNotInstalledError as a documented subclass of LlmConfigError.

### Requirement 7: Database migrations

**User Story:** As the developer, I want Alembic migrations with the pgvector extension enabled, so that later phases can add vector columns.

#### Acceptance Criteria

1. THE Migrations SHALL be located in `backend/app/db/` and use an async SQLAlchemy engine with the asyncpg driver.
2. THE Migrations SHALL read the database URL from the Settings.
3. THE Migrations SHALL include a first migration that executes `CREATE EXTENSION IF NOT EXISTS vector`.
4. WHEN `uv run alembic upgrade head` is run against the Database, THE Migrations SHALL leave the `vector` extension installed in the `screen_to_cart` database.
5. WHEN the first migration is applied to a database where the `vector` extension already exists, THE Migrations SHALL complete without error.

### Requirement 8: FastAPI application and health endpoint

**User Story:** As the developer, I want a FastAPI app with a health check the extension can call, so that I can confirm the backend is reachable.

#### Acceptance Criteria

1. THE Backend SHALL define the FastAPI application in `backend/app/main.py`.
2. WHEN a `GET /health` request is received, THE Health_Endpoint SHALL return HTTP 200 with a JSON body defined by a Pydantic model in `backend/app/schemas.py`.
3. THE Backend SHALL include the Health_Endpoint response model in the `/openapi.json` schema.
4. THE Backend SHALL allow cross-origin requests from the Extension's origin through CORS middleware.
5. THE Backend SHALL read the allowed Extension origin from the Settings.
6. WHEN a `GET /health` request is received, THE Health_Endpoint SHALL respond without calling an LLM provider or a retailer API.

### Requirement 9: Langfuse observability

**User Story:** As the developer, I want Langfuse tracing set up with per-request handlers and named traces, so that every request can be inspected and filtered by provider.

#### Acceptance Criteria

1. THE Observability_Module SHALL configure the Langfuse client from LANGFUSE_PUBLIC_KEY, LANGFUSE_SECRET_KEY and LANGFUSE_BASE_URL in the Settings.
2. THE Observability_Module SHALL provide a helper that returns a new Langfuse `CallbackHandler` instance on each call.
3. WHEN the CallbackHandler helper is called twice, THE Observability_Module SHALL return two distinct CallbackHandler instances.
4. THE Observability_Module SHALL provide a helper that wraps a run in `propagate_attributes` with a trace name, an optional session id and tags containing the Provider_Tag.
5. THE Observability_Module SHALL re-export the Langfuse `observe` decorator for use by non-LangChain code.
6. WHEN a `GET /health` request is received, THE Health_Endpoint SHALL execute inside an `@observe()` span wrapped in `propagate_attributes` with a fixed trace name and the tag `groq-free`.
7. WHEN a `GET /health` request is received with valid Langfuse credentials, THE Backend SHALL produce a Langfuse trace with the Health_Endpoint's trace name and the tag `groq-free`.
8. IF Langfuse credentials are missing, THEN THE Observability_Module SHALL disable tracing so that the Tracing_Wrapper runs as a no-op, and THE Health_Endpoint SHALL return HTTP 200.
9. IF the Langfuse host is unreachable when traces are exported in the background, THEN THE Health_Endpoint SHALL return HTTP 200.
10. (Removed on 2026-10-30 as over-engineering: no special handling for tracing setup errors.)

### Requirement 10: Extension project

**User Story:** As the developer, I want the extension scaffolded with WXT's React template and the planned packages, so that later phases can build the side panel and API calls on it.

#### Acceptance Criteria

1. THE Extension SHALL be created with `pnpm dlx wxt@latest init extension` using the React template.
2. THE Extension SHALL set `"name": "screen-to-cart-extension"` in `extension/package.json`.
3. THE Extension SHALL set `manifest.name` to `Screen to Cart` in `extension/wxt.config.ts`.
4. THE Extension SHALL set `manifest.description` to `Find anything you see in a video, compared across stores.` in `extension/wxt.config.ts`.
5. THE Extension SHALL list `@microsoft/fetch-event-source` and `openapi-fetch` as dependencies added with `pnpm add`.
6. THE Extension SHALL list `openapi-typescript` as a dev dependency added with `pnpm add -D`.
7. THE Extension SHALL include a committed `pnpm-lock.yaml` file.
8. THE Extension SHALL declare the `sidePanel` permission and register a side panel entrypoint in `extension/entrypoints/sidepanel/`.

### Requirement 11: Generated API types and typed client

**User Story:** As the developer, I want the extension's API types generated from the backend schema, so that frontend and backend payloads cannot drift.

#### Acceptance Criteria

1. THE API_Types SHALL be generated by running `openapi-typescript` against the Backend's `/openapi.json`.
2. THE Extension SHALL contain API payload types only in the generated API_Types, with no hand-written duplicates.
3. THE Extension SHALL provide a script in `extension/package.json` that regenerates the API_Types from `http://localhost:8000/openapi.json`.
4. THE API_Client SHALL be built with `openapi-fetch` typed by the API_Types.
5. THE API_Client SHALL read the Backend base URL from Extension build-time configuration.

### Requirement 12: Side panel health check

**User Story:** As the developer, I want the side panel to confirm the backend is reachable, so that I can see the full stack working end to end.

#### Acceptance Criteria

1. WHEN the Side_Panel opens, THE Side_Panel SHALL send a `GET /health` request through the API_Client.
2. WHEN the Health_Endpoint returns HTTP 200, THE Side_Panel SHALL display the text `backend OK`.
3. IF the `GET /health` request fails or returns a non-200 status, THEN THE Side_Panel SHALL display a message stating that the backend is unreachable.
4. WHILE the `GET /health` request is pending, THE Side_Panel SHALL display a checking status.

### Requirement 13: Testing without live services

**User Story:** As the developer, I want tests that never call live LLM or retailer APIs, so that tests do not consume free-tier quota.

#### Acceptance Criteria

1. THE Test_Suite SHALL run with `uv run pytest`.
2. THE Test_Suite SHALL execute without sending requests to any LLM provider or retailer API.
3. THE Test_Suite SHALL cover the Settings sponsorship fallback to REFINE_MODEL and the LLM_MODE validation.
4. THE Test_Suite SHALL cover the LLM_Factory for a `groq` Model_Spec, an `anthropic` Model_Spec without `langchain-anthropic` installed, an invalid Role, an unsupported provider and a malformed Model_Spec.
5. THE Test_Suite SHALL cover the Health_Endpoint returning HTTP 200 with Langfuse disabled or mocked.
6. (Removed on 2026-10-30: `new_callback_handler()` is a one-line constructor call; no dedicated test.)
7. THE Test_Suite SHALL obtain configuration from test-provided values without reading the Env_File.
8. THE Test_Suite SHALL assert that the LLM_Factory raises ProviderNotInstalledError for an `anthropic` Model_Spec without `langchain-anthropic` installed.

### Requirement 14: Phase 0 completion

**User Story:** As the developer, I want a clear end-to-end check for Phase 0, so that I know the setup is complete before starting Phase 1.

#### Acceptance Criteria

1. WHEN `docker compose up` is run with a valid Env_File, THE Compose_Stack SHALL bring up the Database and the Backend.
2. WHEN the Extension is loaded in Chrome and the Side_Panel is opened while the Compose_Stack is running, THE Side_Panel SHALL display `backend OK`.
3. WHEN the Side_Panel health check completes with valid Langfuse credentials, THE Backend SHALL produce a trace in the Screen to Cart Langfuse project with the Health_Endpoint's trace name and the tag `groq-free`.
